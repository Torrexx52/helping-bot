# Helping Bot — спецификация

Версия 1.0 · 7 ноября 2026 · владелец: Черемисин А. С. (единственный пользователь)

## 1. Цель

Личный Telegram-бот, который выдаёт готовые посты для соцсетей из приватных GitHub-репозиториев проектов. Посты заранее пишут ИИ-агенты (ChatGPT, Codex, Claude) или сам владелец и кладут в репозиторий проекта в фиксированном формате. Бот показывает очередь постов по аккаунту. По выбору поста бот присылает медиа, описание и подпись с хэштегами, которую можно скопировать одним нажатием. Публикует пост в TikTok сам владелец вручную.

Долгосрочно Helping Bot должен стать универсальным ботом для работы с соцсетями: редактор и автопостинг в Telegram-каналы, аналитика. **В v1 этого нет**, но архитектура не должна этому мешать (см. §9).

## 2. Термины

- **Проект** — продукт владельца, например «Эзотерика» (таро, астрология, матрица судьбы). У проекта один или несколько контент-репозиториев.
- **Контент-репозиторий** — приватный GitHub-репозиторий, в котором лежат посты. Подключается через конфиг на сервере.
- **Аккаунт** — конкретная страница в соцсети, например `tiktok-esoteric` (TikTok, эзотерика). У каждого аккаунта своя очередь постов.
- **Пост** — папка с `post.md` и медиафайлами (формат описан в `docs/CONTENT_FORMAT.md`).

## 3. Пользовательский сценарий v1

1. Владелец отправляет `/start`. Бот проверяет Telegram ID; всех, кроме владельца, игнорирует (максимум отвечает «Бот приватный»).
2. **Главное меню.** Нижняя клавиатура (ReplyKeyboardMarkup) с кнопкой на каждый аккаунт, например `🔮 TikTok · Эзотерика`, и кнопкой `🔄 Обновить всё`.
3. **Очередь аккаунта.** После нажатия на аккаунт бот присылает сообщение со списком неопубликованных постов, по 5 на страницу:
   ```
   🔮 TikTok · Эзотерика — к публикации 12 (стр. 1/3)
   1. 10.11 · Карта дня — Башня 🎞
   2. 11.11 · Ретроградный Меркурий 🖼×6
   3. ...
   ```
   Нижняя клавиатура меняется: `1 · Карта дня — Башня`, `2 · Ретроградный…` (название обрезается примерно до 24 символов), затем ряд `◀️ Назад` `▶️ Далее` и ряд `🔄 Обновить` `🏠 Меню`. «Назад» и «Далее» показываются только там, где есть куда листать.
4. **Карточка поста.** После нажатия на номер бот присылает по порядку:
   1. медиа: одно видео, одно фото или альбом (media group) из нескольких фото или видео в порядке имён файлов;
   2. сообщение с информацией: заголовок, дата и все разделы `post.md`, кроме подписи (например «О чём пост», «Звук», «Заметки»);
   3. сообщение с подписью для TikTok внутри `<pre>`. На телефоне такой блок копируется одним нажатием. Если подпись не длиннее 256 символов, к сообщению добавляется inline-кнопка `📋 Копировать` (`CopyTextButton`);
   4. inline-кнопки `✅ Опубликовал` и `⏸ Отложить`. Их можно повесить на сообщение с подписью.
5. **✅ Опубликовал** — пост получает статус `published` и время публикации и исчезает из очереди. Бот отвечает «Отмечено ✅» и снова показывает очередь (ту же страницу).
6. **⏸ Отложить** — пост уходит в конец очереди: получает `postponed_at = now` и показывается после всех неотложенных, с пометкой ⏸. При повторном откладывании время обновляется.
7. **`/published`** (необязательно, но желательно) — последние 20 опубликованных постов с кнопкой «↩️ Вернуть в очередь» на случай ошибки.

### Порядок очереди
Неопубликованные посты аккаунта: сначала неотложенные по возрастанию `date` из frontmatter (при равных датах — по пути папки), затем отложенные по возрастанию `postponed_at`. Посты без `date` идут в конец неотложенных.

## 4. Источник данных и синхронизация

- Сервер держит **локальный клон** каждого контент-репозитория в `data/repos/<repo_id>/`. Видео небольшие, поэтому место на диске не проблема. Отдельной копии постов, кроме клона, нет.
- Индекс постов (путь, заголовок, дата, аккаунт, хэш содержимого) хранится в SQLite и пересобирается после каждой синхронизации.
- **Статусы** (`published`, `postponed_at`) хранятся **только в SQLite на сервере**. В репозиторий бот ничего не пишет: в v1 доступ только на чтение. Ключ поста — `repo_id + путь папки`. Если папку переименовать, пост станет новым; это допустимо.
- **Когда синхронизировать:**
  1. **GitHub webhook** на `push` — основной способ: после push бот подтягивает изменения в течение нескольких секунд. Подпись проверяется по `X-Hub-Signature-256` с секретом репозитория. Эндпоинт: `POST https://vibee.ddns.net/hooks/helping-bot/github`. Nginx Cargo-сайта проксирует его на `127.0.0.1:8081`.
  2. **Фоновый опрос** каждые 15 минут (`git fetch`) — подстраховка, если webhook не дошёл.
  3. Кнопки `🔄 Обновить` и `🔄 Обновить всё` — ручная синхронизация.
- Синхронизация: `git fetch --depth=50 origin <branch>`, затем `git reset --hard origin/<branch>`. Одновременно идёт не больше одной синхронизации на репозиторий (asyncio.Lock).
- Невалидный пост (нет `post.md`, нет раздела подписи, неизвестный аккаунт, нет медиа) в очередь не попадает. Бот пишет его в лог, а в очереди внизу показывает строку «⚠️ 2 поста с ошибками — /errors». Команда `/errors` выводит путь и причину.

## 5. Отправка медиа

- Фото: `.jpg .jpeg .png .webp`; видео: `.mp4 .mov`. Сортировка по имени файла с естественным порядком: `2.jpg` идёт раньше `10.jpg`.
- Один файл отправляется через `send_photo` или `send_video`. От 2 до 10 файлов уходят одним `send_media_group`. Больше 10 — несколько альбомов подряд.
- **Кэш file_id.** После первой отправки Telegram возвращает `file_id`. Его нужно сохранить в SQLite по ключу `(repo_id, path, sha256 файла)` и при повторных показах отправлять файл по `file_id`, без повторной загрузки.
- Фото больше 10 МБ отправляется как документ; файлы больше 50 МБ не отправляются, вместо них приходит сообщение-ошибка (лимит обычного Bot API).
- Если медиа нет совсем, пост считается невалидным.

## 6. Конфигурация

Секреты передаются через `.env`, проекты описываются в `config/projects.yml` на сервере. Новый репозиторий подключает агент: добавляет блок в `projects.yml` и перезапускает контейнер (или выполняет `/reload`). Пример лежит в `config/projects.example.yml`.

`.env`:
```
BOT_TOKEN=            # от @BotFather
OWNER_TELEGRAM_ID=    # числовой ID владельца
GITHUB_TOKEN=         # fine-grained PAT: Contents=Read-only на нужные репозитории
WEBHOOK_HOST=127.0.0.1
WEBHOOK_PORT=8081
SYNC_INTERVAL_MIN=15
LOG_LEVEL=INFO
TZ=Europe/Moscow
```

Секреты webhook для каждого репозитория задаются в `projects.yml` через ссылку на переменную окружения: `webhook_secret_env: GH_SECRET_ESOTERIC`.

## 7. Технологии

- Python 3.12, **aiogram 3.x** (long polling для Telegram), aiohttp-сервер внутри того же процесса для GitHub webhook.
- SQLite через `aiosqlite`; схема создаётся миграциями при старте.
- `python-frontmatter`, `PyYAML`; git — через системный `git` в subprocess, токен передаётся в URL клона `https://x-access-token:<TOKEN>@github.com/...`. Токен не должен попадать в логи.
- Docker + Docker Compose. Один сервис `bot`, тома `./data:/app/data` и `./config:/app/config:ro`, порт публикуется только на `127.0.0.1:8081`.
- Тесты: `pytest` на парсер `post.md`, сортировку очереди, пагинацию и проверку подписи webhook.
- Линт: `ruff`.

## 8. Развёртывание

- Сервер — VPS №2223763 (`ssh vibee-root`, `2.26.64.167`, Debian 12, Docker CE уже установлен, контейнеров нет). Подробности и правила — в `docs/SERVER.md`.
- Каталог `/opt/helping-bot`: клон репозитория бота, рядом `.env`, `config/projects.yml`, `data/`.
- Сервер получает репозиторий бота по deploy key (read-only), который агент создаёт на сервере.
- `scripts/deploy.sh` (запускается на сервере): `git pull` → `docker compose up -d --build` → проверка `docker compose ps` и healthcheck.
- Nginx: в `/etc/nginx/sites-enabled/cargo` добавить только `location = /hooks/helping-bot/github { proxy_pass http://127.0.0.1:8081; }` внутри server-блока на 443, затем `nginx -t` и `systemctl reload nginx`. Перед правкой сохранить копию конфига.
- Резервная копия: ежедневный `sqlite3 .backup` в `/var/backups/helping-bot/` с ротацией 14 дней, через cron или systemd timer.
- Healthcheck: `GET 127.0.0.1:8081/health` → `200 ok`.

## 9. Задел на будущее (не делать в v1)

Код нужно организовать так, чтобы следующие функции добавлялись без переписывания:
- **Платформы как адаптеры.** У аккаунта есть поле `platform` (`tiktok`, позже `telegram_channel`, `instagram`, `youtube_shorts`). Отрисовка карточки и действие «опубликовать» зависят от платформы: для TikTok это ручная публикация, для Telegram-канала в будущем бот сам будет публиковать пост.
- **Редактор постов** для Telegram-каналов: правка текста в боте или в Mini App, запись изменений обратно в GitHub. Для этого понадобится PAT с правом записи.
- **Аналитика:** таблица `post_metrics`, ручной ввод цифр или автоматический сбор по Telegram-каналам.
- **Несколько пользователей:** сейчас доступ только у владельца, но проверку прав нужно вынести в отдельный middleware.

## 10. Критерии готовности v1

1. После `/start` у владельца открывается меню с аккаунтами из `projects.yml`; чужой пользователь доступа не получает.
2. Тестовый пост, запушенный в контент-репозиторий, появляется в очереди не позже чем через минуту, без ручных действий.
3. Очередь листается по 5 постов, порядок соответствует §3.
4. Карточка поста приходит полностью: медиа (одиночное и альбом), информация, подпись в `<pre>` и кнопки.
5. «Опубликовал» убирает пост из очереди; «Отложить» переносит его в конец. Оба состояния сохраняются после перезапуска контейнера.
6. Невалидный пост не ломает бота и виден в `/errors`.
7. Контейнер работает на `vibee-root` с `restart: unless-stopped`, Cargo-сайт по-прежнему отдаёт HTTPS 200, SSH доступен.
8. В README описано, как подключить новый репозиторий и как задеплоить.
